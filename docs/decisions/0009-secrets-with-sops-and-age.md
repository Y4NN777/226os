# ADR-0009 — Secrets with SOPS and age

- **Status:** ACCEPTED
- **Date:** 2026-11-12
- **Approver:** `Y4NN77`, repository owner ("we will use sops for secrets", 2026-11-12)
- **Scope:** how the project's secrets (database password, cursor-signing key, SMTP and AI Studio credentials) are stored, shared, deployed and rotated
- **Amends:** the rule "secrets never in Git" of [ADR-0006](0006-toolchain-environments-quality-commands.md) and `docs/SHIP.md`: encrypted secrets MAY be committed; plaintext never.
- **Related:** [ADR-0003](0003-authentication-sessions-csrf-rate-limits.md), `scripts/secrets.sh`, `scripts/check-secrets-encrypted.sh`, `.env.example`

## Context

Until now each profile's secrets lived only in a git-ignored `.env.<profile>` on one machine. That does not share, review or version anything, and a lost laptop loses the staging password. The team needs a way to keep secrets next to the code, reviewable as a diff of names, recoverable, and usable on the deployment host, without a cloud account or a server to run.

## Options considered

- **SOPS + age (chosen):** files in Git, values encrypted per recipient with age public keys, no server, no cloud account, tools already available (`sops`, `age`). A recipient list per profile limits who can decrypt production.
- **Cloud KMS or a secret manager (Vault, AWS, GCP):** more features and rotation, but an account, an always-on dependency and cost; out of proportion for four people and one host.
- **A password manager and copy-paste:** nothing in Git, but no review, no versioning, easy to drift between environments.
- **git-crypt:** transparent but encrypts whole files, so a diff shows nothing and the recipients model is weaker.

## Decision

1. **Layout.** `secrets/<profile>.enc.env` (dotenv format: variable NAMES in clear, every non-empty VALUE an `ENC[AES256_GCM,...]` envelope) and `secrets/<profile>.recipients` (PUBLIC age keys, one per line). Profiles: `local-dev` (optional), `staging-test`, `production-live`. Both files are committed; nothing else belongs in `secrets/` except a `README.md`.
2. **Keys.** Every person has their own private age key at `~/.config/sops/age/keys.txt` (`scripts/secrets.sh keygen`). It is never committed, never printed, never copied. Only PUBLIC keys go in the repository. Recipients differ per profile: `production-live` lists only the owner and the deployment host key; developers may be listed for `local-dev` and `staging-test`.
3. **One entry point.** `scripts/secrets.sh` (`keygen`, `init`, `edit`, `decrypt`, `rotate`, `check`) is the only supported way to touch these files. `init` encrypts the `.env.example` placeholders (comments stripped); `edit` goes through `sops edit`; `decrypt` writes a git-ignored `.env.<profile>` (mode 600, refuses to overwrite without `--force`); `rotate` re-encrypts for the CURRENT recipients with a fresh data key. New files are staged next to their target and renamed into place, so a failure never leaves a half-written secrets file. KMS, PGP and Vault key groups from the caller's environment are ignored: only the age recipients count. A pasted private key is never echoed. **Plaintext handling, stated honestly:** `init`, `rotate` and the runtime decryption keep plaintext in a private directory (RAM-backed `/dev/shm` when available, else the system temp dir) and remove it on exit; `sops edit` keeps its own temporary plaintext, which this script does not control; a `SIGKILL` can leave plaintext behind (`/dev/shm/secrets.*`, `.env.<profile>.partial.*`, all mode 600 and git-ignored).
4. **Gate (a FORMAT check, not an integrity proof; only `sops decrypt` proves integrity).** `scripts/check-secrets-encrypted.sh` runs in `make security` and fails when anything under `secrets/` is not what sops writes: a symlink, a stray file, a file over 256 KiB, a comment, a private age key, a key name that is not `UPPER_SNAKE_CASE`, a value that is neither empty (sops leaves empty values empty) nor a full `ENC[AES256_GCM,data,iv,tag,type]` envelope with the exact `iv` and `tag` lengths, a `sops_` key that is not one of the exact metadata keys (each with its value format), a missing `sops_mac`, `sops_version` or recipient. It also requires every encrypted file to have a `<profile>.recipients` file whose keys EQUAL the file's recipients, so removing a person without running `rotate` shows up as a failure. It sets `LC_ALL=C` so the verdict does not depend on the locale, and it is pure bash, so CI needs neither `sops` nor `age`. **Residual:** an `UPPER_SNAKE_CASE` key name, a base64 `data` field and free-text comments (at most 80 characters, in `.recipients`) can still carry a small amount of plaintext; that is caught by review of the diff, not by the gate.
5. **Secret scanner.** No allowlist: gitleaks keeps scanning `secrets/` with its default rules. Measured with the pinned image (v8.30.0): real `sops` output with password, key and SMTP-password names is NOT flagged (the envelope's punctuation breaks the scanner's key-value pattern), while the same names with plaintext values in a `.env` ARE flagged. The two defenses OVERLAP but are not independent guarantees: the scanner misses plaintext that has no keyword, and the gate cannot see plaintext hidden in an allowed shape (see item 4). The reviewer's measured result is that a plaintext secret smuggled under a key name or a base64 `data` field can pass both.
6. **Runtime decryption.** `scripts/compose.sh <profile> ...` (so `make up-local-dev` and every deploy command) takes its environment from, in order: an explicit `COMPOSE_ENV_FILE`; the encrypted `secrets/<profile>.enc.env`, which it decrypts into a private RAM-backed temporary file for that one command and removes on exit (no plaintext `.env` on disk, none inside the repository); a plain `.env.<profile>`. The encrypted file wins over a plain `.env.<profile>`, which is then ignored with a notice, so a stale local file cannot shadow the reviewed secrets. The private key of the deployment host lives only on that host. CI never decrypts anything: it has no private key and `make quality` needs none. `scripts/secrets.sh decrypt` remains for the rare case where a plaintext file is wanted.
7. **Rotation and leaks.** Removing a person or a host: remove its line from `<profile>.recipients`, run `scripts/secrets.sh rotate <profile>`, and CHANGE the underlying secrets that person could read (re-encryption does not unsee what they already decrypted). A leaked private age key means rotating every secret of every profile it could decrypt.
8. **Out of scope.** Cloud KMS, per-variable access control (a recipient decrypts the whole profile), automatic rotation, and storing the staging or production private key in CI.

## Consequences

- **Security:** secrets are reviewable by name in diffs and recoverable from Git history, but the history is permanent: a value committed under a compromised key stays decryptable by whoever holds that key, so rotation is mandatory after any key loss. The recipient list is the access-control list; changing it is a security review item.
- **Operations:** a new teammate cannot decrypt anything until an existing recipient adds their public key and rotates. The deployment host key must be backed up by the owner.
- **Quality:** `make security` gains one fast, dependency-free check with 29 test cases. The wrapper's round trip (init, decrypt, rotate, the wrong key, KMS variables ignored, no leftovers) and the runtime decryption through `compose.sh` need `sops` and `age`: where they are missing the tests print NOT RUN, and in GitHub Actions they emit a `::warning` annotation so it is visible on the pull request. CI therefore verifies the check script but not the round trip; run `scripts/tests/secrets_test.sh` and `scripts/tests/compose-secrets_test.sh` locally after changing the scripts.
- **Cost:** none.

## Evidence / verification required

`scripts/tests/check-secrets-encrypted_test.sh` (plaintext value, missing metadata, comment, private key, stray file, empty value) and `scripts/tests/secrets_test.sh` (arguments and refusals everywhere; the init, decrypt, rotate round trip with real `sops` and `age` where installed, including that real `sops` output passes the check and that a newly added recipient can decrypt). The pinned gitleaks image, on default rules, flags a planted key and a plaintext `.env` but not real `sops` ciphertext. Gate G4.
