# ADR-0013 — Default branch `develop`: pipeline trust anchor

- **Status:** ACCEPTED (owner `Y4NN777`, 2026-11-14)
- **Date:** 2026-11-14
- **Approver:** `Y4NN777`, repository owner
- **Scope:** which branch is the GitHub default branch, and what that means for the AI review pipeline (stages 3 to 5) and for who may change it. The promotion `develop` to `main` is not changed.
- **Answers:** TODO "AI review" block (stages 3, 4 and 5 were NOT RUN before the promotion to `main`).
- **Related:** `.github/workflows/review-autofix.yml`, `review-automerge.yml`, `review-batch.yml`, `review-merged.yml`, `.github/pipeline-paths.txt`, `.github/CODEOWNERS`, `scripts/review-automerge.py`, `scripts/close-merged-issues.py`, `scripts/tests/review-agent-triggers_test.sh`, [ADR-0008](0008-team-work-areas-and-ownership.md), [`GIT_WORKFLOW.md`](../GIT_WORKFLOW.md), [`REVIEW_CONTEXT.md`](../quality/REVIEW_CONTEXT.md)

## Context

GitHub runs a workflow started by `workflow_run`, `schedule` or `workflow_dispatch` only from the copy of the file on the default branch, which is `main` today ([events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)). Three stages of the review pipeline use those events:

- stage 3, auto-fix (`review-autofix.yml`): `workflow_run` after "Code review";
- stage 4, auto-merge (`review-automerge.yml`): `workflow_run` after Quality, Code review or Branch policy, and `workflow_dispatch`;
- stage 5, batch and batch fix (`review-batch.yml`): `schedule` every 5 hours and `workflow_dispatch`.

Work lands on `develop` and reaches `main` only by the production promotion, so none of the three could run before the first release: a manual dispatch or a schedule returns 404 and a `workflow_run` never fires. The pipeline needs the default branch to hold the workflows it runs, and it must trust that branch, because the default branch's copy of a workflow and of its scripts runs with `REVIEW_AGENT_TOKEN` (environment `review-agent`) and a write token.

## Decision

1. **The default branch becomes `develop`.** The owner switches it (Settings, General) after this ADR merges. `main` stays the production branch; promotion, back-merge, branch protection and the required checks of [`GIT_WORKFLOW.md`](../GIT_WORKFLOW.md) are unchanged.
2. **`develop` is the pipeline trust anchor.** Stages 3 to 5 run from `develop`'s copy of the workflows and scripts. The `review-agent` environment allows the deployment branch `develop` only (`main` removed, done 2026-11-14), so a run from another branch cannot read the token. A `workflow_dispatch` can name any ref and runs that ref's copy of the workflow; so can a push to another branch. Only this deployment-branch rule keeps `REVIEW_AGENT_TOKEN` from such a run, which is why this decision matters: it is the control, not a convention.
3. **Pipeline paths are protected by convention and by auto-merge, not by a ruleset.** `.github/pipeline-paths.txt` lists them. Auto-merge runs `develop`'s own copy, so a pull request cannot change it before it merges; it refuses any pull request that touches those paths (label `needs-owner`, one-line reason). Only the owner merges a pull request that touches them; teammates do not. `.github/CODEOWNERS` is unchanged (it starts with `* @Y4NN777`).
4. **A static guard keeps the token out of pull request events.** `scripts/tests/review-agent-triggers_test.sh` (run by `make lint-scripts`) fails when a job that declares `environment: review-agent` can be started by `pull_request`, `pull_request_review` or `pull_request_target`. A job is accepted in a workflow that also has a pull request trigger only when it, or a job it needs, is guarded by a `github.event_name` test for a non-pull-request event (today `review-batch.yml`, whose `publish` job needs `plan`, itself limited to `schedule` and `workflow_dispatch`). The guard fails closed: it reads the text without a YAML library, and whatever it cannot read with certainty takes the dangerous reading. An `environment` that is not a plain name (expression, anchor, alias, flow mapping), an `on:` it cannot read (alias, flow mapping, missing) and a flow-mapping job all count as holding `review-agent` or as every pull request trigger; an `if:` is a guard only in the narrow `&&` forms it knows; a guard that comes only from `needs:` does not survive `always()` unless the job also requires an output of the guarded job; anchors, aliases and merge keys in a workflow with an environment are refused. So the test can refuse a safe file, never accept an unsafe one.
5. **Closing keywords now act natively on `develop`.** `Closes #N` and `Fixes #N` close issues on a merge into the default branch, including `needs-owner` issues. This is wanted since the initial design. Batch issues are unaffected: the batch pull request says `Batch: #N`, which is not a closing keyword. `scripts/close-merged-issues.py` stays: it is idempotent and closes what GitHub may not (for example a keyword written in another case or form, with its single comment).

## Consequences

- Stages 3, 4 and 5 run from `develop` once the default branch is switched. Until then they stay NOT RUN. After the switch the owner runs four smoke checks: the three workflows appear in `gh api repos/{owner}/{repo}/actions/workflows`; a `workflow_dispatch` of Review auto-merge on an open pull request with `AUTO_MERGE=report` prints WOULD MERGE or REFUSE; a dispatch of Review batch with `AUTO_FIX=report` prints the batch decision; a pull request with an open MEDIUM finding shows stage 3's report-mode decision. `AUTO_FIX` and `AUTO_MERGE` move from `report` to `on` when the reports look right. All NOT RUN today.
- **Trust level unchanged in practice.** `develop` already reaches `main` with 0 approvals on promotion, and `develop` requires no review. The anchor moves to a branch that is protected by the same required checks (`quality`, "Validate branch promotion"), conversation resolution, no force-push and enforced admins.
- **The pipeline-path protection is a convention (owner decision 3, accepted by Y4NN777 on 2026-11-14; not a gap).** A teammate with write access could merge a pull request that touches the pipeline paths: nothing stops it technically. Mitigations: auto-merge refuses it, the review marks it `needs-owner`, and ADR-0008 makes the pipeline the owner's area. A pull request that edits `code-review.yml` runs its own copy of the gate, so the gate cannot protect these paths; this is why the owner reads and merges them.
- **Side effects.** New clones check out `develop` and a pull request opened without a base targets `develop` (the branch the policy wants). `branch-policy.yml` is unchanged: work branches target `develop`, and only `develop` or `hotfix/*` may target `main`. Issues named by a closing keyword close on merge into `develop`, including `needs-owner` ones.
- **Decided by the owner (Y4NN777, 2026-11-14): `REVIEW_AGENT_TOKEN` stays the owner's own fine-grained token** (this repository, Contents and Pull requests read and write, no Workflows), not a machine account. Accepted consequence: an action taken with it is recorded as the owner's, and it could approve a pull request as the owner and so satisfy the owner-approval condition of auto-merge. What limits it: exactly three jobs declare the `review-agent` environment and read the token, and no other job can: job `automerge` of `review-automerge.yml` (line 48; `scripts/review-automerge.py` merges with it, updates other branches, adds the `needs-owner` label and a comment), job `publish` of `review-autofix.yml` (line 286; one `git push` of the fix to the head branch) and job `publish` of `review-batch.yml` (line 302; one `git push` of the batch branch and `gh pr create`). That environment allows `develop` only (decision 2), and the scripts that use the token run from `develop`'s copy. Verified 2026-11-14 by grep over `review-automerge.py`, `review-autofix.py`, `findings.py`, `close-merged-issues.py` and the four review workflows: no code path approves a pull request with this token. The only `/reviews` call is a read (`review-automerge.py` `owner_approved_head`, line 102; `review-gate.py` reads it too, with the workflow token); there is no `gh pr review`, no `APPROVE` event and no review POST, and `findings.py` and `close-merged-issues.py` (run by `review-merged.yml` with the workflow token) never see the secret.

## Alternatives considered

- **Trigger on `pull_request`, `pull_request_review` or `pull_request_target` instead of `workflow_run`.** Rejected. `pull_request` from a fork has no secrets and a read-only token, and a same-repository run executes the pull request's own copy of the workflow, so the code under review would choose the code that holds the write token. `pull_request_target` runs the base copy but is the classic injection path when it touches pull request text or a checkout, and it is blocked by default from 2 December 2026 ([changelog](https://github.blog/changelog/2026-11-02-pull_request_target-blocked-by-default-december-2); see also [environment branch protection changes](https://github.blog/changelog/2025-11-07-actions-pull_request_target-and-environment-branch-protections-changes/)). The project forbids it with a pull request checkout. The guard in decision 4 enforces this.
- **`check_run` or `check_suite` triggers.** Rejected: same default-branch rule as `workflow_run`, so nothing is gained, and the event carries less context.
- **A `push` trigger as a fallback for stage 5 only.** Rejected as the main answer: it fixes only the batch, leaves stages 3 and 4 waiting for the release, and runs on every push instead of on a schedule. It stays the fallback if the owner refuses the switch.
- **Promote the pipeline workflows to `main` early.** Forbidden by [`GIT_WORKFLOW.md`](../GIT_WORKFLOW.md): `main` receives only a promotion from `develop` (and a hotfix), a partial promotion would put untested files on the production branch, and `Validate branch promotion` would then block every pull request until a back-merge.
- **An external cron or an always-on job elsewhere.** Rejected: `workflow_dispatch` still needs the file on the default branch, and an external scheduler needs the token stored outside GitHub, a new attack surface for no gain.
- **A ruleset requiring code-owner review on the pipeline paths.** Rejected by the owner: `CODEOWNERS` starts with `* @Y4NN777`, so every pull request would wait for the owner and auto-merge would stop. It would also need a bypass for the owner whose exact behaviour for code-owner review is [unverified in the ruleset documentation](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository). Decision 3 replaces it.
